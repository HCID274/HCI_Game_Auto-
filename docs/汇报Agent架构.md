# 双游戏汇报 Agent

## 目标

星铁和鸣潮共享证据切片、脱敏、DeepSeek 调用与 Token 统计，但保留各自适合的汇报方式。星铁继续使用事实项改写；鸣潮把同日已结算阶段按时间合并后，通过一次 DeepSeek 调用直接生成完整日报。

## 数据流

1. 每个运行只读取自己的新增日志；鸣潮同一自然日的独立讨伐和日常阶段以最终成功状态合并，已被后续成功解决的失败不再作为最终异常。
2. 合并后的日志保持时间顺序，经固定无害噪声过滤、脱敏和有界切片后一次性交给 DeepSeek；程序确认的状态和结果同时作为事实边界。
3. 鸣潮模型直接返回 `summary/daily/weekly/followup/issues`，不再逐个事实 ID 机械改写。程序只校验 JSON 结构与成功/失败语义，失败步骤不能被模型删除。
4. 请求使用流式接收；成功报告采用低推理预算，异常报告采用较高预算。模型调用失败时，仍以同一份整日事实生成完整确定性报告。
5. 归档事实、叙述和 `ai_token_usage`；发送前只组装一张最终卡片。预览模式不触发 Webhook。

## Token 统计

归档字段 `ai_token_usage` 包含 `input_tokens`、`output_tokens`、`total_tokens`、`output_input_ratio`、缓存输入、推理 Token、模型和 `available`。比例定义为 `output_tokens / input_tokens`，缺少供应商用量时不估算。

## 安全和边界

- Agent 不得新增不存在的任务、掉落、计数、奖励或完成状态；未确认的活跃度不能改写为已领取。
- 失败报告只说明未成功步骤、相关错误和恢复结果，不展示无业务影响的固定上游警告。
- 日志、结构化事实、回退文本、卡片诊断和归档统一做凭据脱敏。
- 上游 OK-WW/M7A 源码不在此管线内修改；上游更新后只需重新解析当前运行日志。
