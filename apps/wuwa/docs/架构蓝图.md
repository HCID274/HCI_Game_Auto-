# 鸣潮自动化架构蓝图

## 主链路

```text
Windows Task Scheduler (05:30)
  -> 总仓 orchestrator/run.ps1
  -> 全局互斥锁
  -> DesktopGuard（交互桌面/系统弹窗准入）
  -> 星铁 daily
  -> 星铁 cleanup（安全交接边界）
  -> DesktopGuard 二次准入
  -> 鸣潮本地虚拟 USB HID
  -> UU 鸣潮加速
  -> 官方启动器（必要时更新，确认实际游戏窗口后交接）
  -> 独立 FarmEchoTask：先讨伐并确认声骸吸收 5/5（最多 1 小时）
  -> 讨伐死亡边界（必要时：退本回血 + 一次定量补吸收）
  -> 纯 OK-WW DailyTask CLI（日常配置不再附加讨伐）
  -> 本轮新增日志切片 + 截图
  -> 确定性事实解析
  -> 关闭鸣潮/OK + 断开加速 + 退出 UU
  -> 唯一最终通知边界
  -> DeepSeek 措辞 + 飞书卡片/本地预览

Windows Task Scheduler (Sunday 08:00)
  -> 同一个全局互斥锁
  -> 若日常仍在运行则有界等待（最多 3.5 小时）
  -> 鸣潮本地虚拟 USB HID + UU
  -> OK-WW GardenTask CLI
  -> 周常事实与汇报
  -> 完整清理
```

星铁业务失败不会阻止鸣潮；但星铁清理连续失败会阻止鸣潮启动。总控结果同时
保留星铁、清理和鸣潮三个退出码，不能用鸣潮成功掩盖星铁失败。
日常与周常是两个独立通知事务：周常等待锁期间不发送消息，获得锁后使用自己的
日志切片运行，最终另发一条周常飞书。日常的前置讨伐、DailyTask 和全部重试只
汇总到一张日常卡片。

## 桌面可靠性

- 安装阶段同时为 Codex 应用包 SID 与全信任 `ChatGPT.exe` 配置入站阻止规则；
  保留正常出站联网。WindowsApps 中的全信任程序路径会随 Codex 更新改变，因此
  每次真实总控启动前都会按当前包清单刷新 TCP/UDP 程序规则，并安全关闭唯一的
  遗留防火墙确认框；`DryRun` 与纯验证模式不修改系统状态。
- UU 操作前枚举可见顶层窗口，明确拦截 `PickerHost` 防火墙提示、UAC、凭据
  对话框和锁屏；未知安全窗口只保存证据，不盲目点击。
- UU 窗口按 HWND 对应 PID 验证，恢复后通过 Win32 输入线程连接前置，并用
  `GetForegroundWindow` 验收；失败日志必须包含实际前台进程。
- 官方启动器只接受鸣潮安装目录内 `launcher_main.exe` 的窗口；动作前同时验证模板
  坐标仍在该窗口内。每个不同按钮画面保存全屏和按钮裁剪后由本地虚拟 HID 点击，
  相同画面最多重试一次，避免下载动画或窗口抖动造成连续误点。“进入游戏”使用独立
  精确模板；更新主按钮用稳定视觉锚点驱动，最长等待 2.5 小时。只有发现真实
  `Client-Win64-Shipping.exe` 窗口才允许启动 OK-WW。
- 游戏进程可能同时创建无标题小窗口、`NVOGLDC invisible` 和真正渲染窗口；只选择
  面积足够、排除 invisible、优先标题“鸣潮”的最大窗口。随后按真实截图依次处理
  “点击连接”、月相观测卡领取和奖励结果关闭。客户端内热更新完成弹窗必须同时命中
  “更新完成，游戏即将重启”正文与“确认”按钮，动作前保存全屏和按钮裁剪，通过虚拟
  HID 确认后等待旧 PID 消失、新客户端出现；未自动重启时重新进入官方启动器状态机。
  世界状态按左上、右上、右下三处分布式
  HUD 的颜色/几何联合判断，避免半透明图标后的场景背景变化，连续两次命中才完成交接。
  任一阶段失败均保存全屏 PNG，以及相关窗口 HWND/PID/标题/矩形和受管进程路径 JSON。
- 未建模阻塞界面不得按偶发状态跳过：先归档完整证据；明确可复现则补模板、状态分支、
  动作后验收和测试，无法判断一次性/周期性时先向用户确认分类。
- OK-WW 运行前在隔离子进程内探测宿主覆盖实际依赖的上游类、方法和窄签名；若更新
  破坏契约则提前失败。探针和覆盖都只存在于宿主进程内，不修改 OK-WW 源码。
- 计划任务 PowerShell 使用隐藏窗口。.NET 进程句柄只等待直接 CLI 进程并读取
  真实退出码，避免游戏或 UU 子进程持有输出句柄而阻塞星铁到鸣潮的交接。

## 事实边界

- 只解析 `runtime/runs/<run_id>/ok-current-run.log`。
- `Daily Task Completed` 是主流程完成边界。
- 日志继续增长表示仍在运行；45 分钟无日志进展才判定停滞。
- 所有失败先截图、保存当前日志，再关闭进程。
- `FarmEchoTask:start wait in combat` 仅表示进入一次战斗检测循环；
  `FarmEchoTask:farm echo ... None` 也可能是同一场战斗的误判脱战，二者都不能
  单独证明击杀。重开界面可以证明一场击杀，但后续任务的真正完成只认实际成功
  吸收声骸达到 5/5。
- 只有同一当前运行切片同时出现 `char dead` 与 `Revive Failed` 才进入死亡恢复。
  恢复发生在游戏清理前，保留鸣潮、UU 与本地虚拟 HID，停止失败的 OK worker，
  复用 OK 的副本退本和传送回血流程。
- 安全恢复成功后，用 `目标5 - 已确认吸收数` 得出补跑量；精确任务优先使用
  自身结构化吸收数，旧版普通任务回退到日志中的成功吸收标记。事务性覆盖用户
  配置，按剩余量启动独立 FarmEcho 补跑，并在所有退出路径恢复配置原字节。
  补跑再次死亡时继续先做安全恢复；只要仍在同一个 1 小时截止时间内，就按最新
  剩余吸收数继续运行。时间耗尽后只恢复与清理，不再开始新战斗。
- 每个待吸收目标允许最多 12 个战斗检测循环，容忍没有掉落或同一 Boss 战中多次
  误判脱战；全量 5 次对应最多 60 个检测循环。吸收阶段另设 1 小时业务墙钟
  上限，整个鸣潮工作流仍受总控 3 小时最终保险约束。
- 重启后若处于已完成关卡，等待画面稳定 4 秒并探测“退出 / 重新挑战”确认框；
  命中时复用场地启动新战斗，旧重开动作不计数，未命中才走正常 F2 传送。
- AI 不决定完成状态，不增加或删除事实项。
- 邮件不进入事实模型，因此 AI 和飞书层均无法输出邮件内容。
- 前置讨伐、补齐、死亡恢复、DailyTask 和多轮重试属于同一业务事务。每个叶子
  运行只归档日志、结果与截图，不触发飞书；两个阶段结束后，才将包含全部尝试的
  复合结果送入清理与唯一最终通知边界。前置讨伐失败时仍尝试 DailyTask，并以
  合并事实报告部分完成。

## 报告分类

- 日常：无音区、结晶波片、梦魇巢穴声骸、每日活跃度、实际执行的先约电台领取。
- 周常：仅本轮实际运行并完成的幻梦游园等周常。
- 后续事件：讨伐强敌、声骸吸收等独立追加目标；分类名称不代表实际执行顺序。
- 异常记录：主流程失败、可选任务失败和清理失败。

“幻梦游园已达到 6000”“无可领取奖励”等没有产生本轮动作的状态不进入成功
报告。讨伐事实始终保留 GUI 的一基编号，例如“讨伐强敌第2项 7次”；这表示
可确认的击杀次数，不等于完成目标。完成条件单列为“吸收声骸5次”。发生死亡
恢复并补齐时，追加“中途倒地1次，已自动退本回血并补吸收声骸2次”。
OK-WW 只记录每日奖励坐标点击时，若此前没有识别到至少 100 点活跃度，报告
只能写“已执行奖励领取操作”，不能升级为“奖励已领取”或“活跃度已满”。

## 用户 Markdown

`UserContext/培养背景.md` 保存可编辑的 Boss、角色和养成用途；
`UserContext/汇报偏好.md` 保存措辞倾向。两者均为低优先级上下文，不能覆盖
原始编号、次数、完成状态、任务分类或异常事实。

## 退出码

- `0`：鸣潮任务与清理均成功。
- `1`：鸣潮业务流程失败。
- `2`：鸣潮业务成功但清理未完全成功。
- 总控 `10`：星铁业务失败（鸣潮仍已尝试）。
- 总控 `20`：鸣潮失败。
- 总控 `30`：星铁桌面无法安全清理，鸣潮未启动。
- 总控 `75`：已有总控实例持有全局锁。
- 总控 `99`：总控自身异常。

## 安装与更新

管理员安装入口为：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ..\..\scripts\install.ps1
```

该入口幂等配置 Codex 包级及全信任程序入站阻止规则、关闭当前遗留的单个防火墙提示框，
并从总仓注册隐藏运行的每日 `Game_Daily_0530` 与周日 08:00
`Game_Wuwa_WeeklyGarden_Sunday`。它不会启动游戏。
