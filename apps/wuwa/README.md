# WW_Auto

鸣潮无人值守日常自动化：本地虚拟 USB HID、网易 UU、官方客户端更新、OK-WW 命令行、
当前运行日志验收、飞书日报卡片和星铁联动调度。

近期故障与修复证据：[2026-09-22 汇报遗漏、领奖中断与启动入口复核](../../docs/2026-09-22-鸣潮汇报与领取故障.md)。

## 日常入口

```powershell
uv sync
uv run wuwa-auto elevate daily
```

独立补跑入口：

```powershell
uv run wuwa-auto elevate farm-echo
uv run wuwa-auto elevate weekly-garden
```

流程只读取本轮新增的 OK-WW 日志。无论成功或失败，都会先保存截图和日志，
随后关闭鸣潮与 OK、断开鸣潮加速并退出 UU。

工作流启动 VIIPER 后会建立仅监听本机、带随机令牌的 HID 控制通道。UU 的悬停和
点击、OK-WW 的讨伐/战斗点击以及死亡恢复点击都通过同一个虚拟 USB 鼠标发出；
上游仍负责识图和任务编排。这样即使 `PostMessage` 被游戏忽略，也不会修改
OK-WW 源码，且上游更新不会覆盖宿主适配。

UU 首页的“立即加速”属于通用动作，不能单独证明目标游戏。每次启动鸣潮加速前都会
先移开鼠标清除旧悬停状态，再识别鸣潮专属卡片并悬停，最后才允许点击新出现的通用
按钮，避免把星铁卡片残留的“立即加速”误当成鸣潮。

正常日常在 UU 连接后关闭残留的官方客户端和启动器，再直接启动 OK-WW；游戏必须由
OK-WW 的 `start_exe=True` 路径拉起并重新枚举窗口，宿主不得先打开游戏再交给 OK-WW。
OK-WW 确认冷启动窗口尺寸稳定后，宿主只聚焦该窗口一次以唤醒首帧；`点击连接` 仍由
OK-WW 自带的 AutoLogin 识别和点击，进入玩法导航后该聚焦钩子不再运行。若此前精确
识别到“网络异常，请检查后重试”，宿主只点击该重试按钮，单个 Worker 最多 3 次；
仍未消失则关闭客户端，让下一名 OK Worker 自行重新拉起并绑定一次，禁止代点登录。
遇到客户端更新时，单独运行官方更新状态机；它完成启动器和客户端内热更新、连续确认
世界 HUD 后，会再次关闭客户端与启动器，把下一次游戏冷启动交还 OK-WW：

```powershell
uv run wuwa-auto elevate client prepare
```

版本日(2026-08-20 起接入)由 `ensure_client_updated` 门禁自动处理,不再依赖手动
prepare。每日工作流在连接 UU 之后、OK-WW 冷启动之前先做"客户端就绪预检":正常日子
启动器打开即见"开始游戏",确认后关闭启动器继续原流程(约半分钟);版本日则分两段——
先处理启动器自更新模态弹窗 `KRUpdateReminderDlg`(窗口枚举定位,模板
`client_launcher_selfupdate_confirm.png` 是弹窗**右下角**大号"更新"按钮本体的 170x110
裁片,点击点=匹配中心,无偏移;弹窗左列是自动后台下载进度与"退出",勿点),自更新
完成后启动器自动重启,再由主界面锚点路径点击右下角"更新"下载游戏版本。自更新点击
后 15 秒内窗口哈希无变化即判定空点、立即重试;下载中窗口哈希 120 秒无变化判定停滞,
关闭启动器重开续传,最多 6 次后按失败上报;总预算 4 小时。下载完成后按星期与时刻
分流:周一至周五白天只更新不进游戏,注册当晚 20:00 一次性计划任务
(`scripts/version_day_evening_rerun.ps1`,只触发一次;脚本不能删除自己,
删除运行中的任务会被 Windows 立即终止)重跑日常并发飞书黄卡;
周末与晚间更新完直接继续当日任务。识别不到任何已知状态的 5 分钟内快速失败,
不占用夜间预算。`Game_Daily_0530` 执行上限已放宽到 6 小时以容纳版本日下载。

模板坐标教训(0820 事故):截图裁剪必须使用 DPI 感知进程的**物理像素**坐标
(`client/launcher.py` 导入即设 DPI 感知,其窗口矩形即物理坐标;非感知的
PowerShell/子进程给出的是 125% 缩放后的逻辑坐标)。当晚用逻辑坐标裁片建模板,
模板"匹配成功"实为错像素自洽,点击点偏离真实按钮 1038 像素,整晚空点。新模板
必须用"从真实坐标裁片 → 在屏幕上反查匹配 → 匹配中心落在预期按钮矩形内"三步
校准,并在初始态与下载态两种状态下分别验证。

真实启动器截图可用 `scripts/crop_client_launcher_templates.py` 重新生成模板；脚本会校验
原图尺寸，防止从错误分辨率静默产出失效坐标。
游戏登录、奖励中间页和网络重试模板由 `scripts/crop_client_game_templates.py` 从真实
2560×1440 截图生成，同样执行尺寸校验。世界状态使用分布在左上、右上和右下的
HUD 颜色/几何联合判定，不把半透明 UI 后方的场景背景固化进模板。
客户端内热更新完成模板由 `scripts/extract_client_update_templates.py` 从失败现场的
2560×1440 全屏证据提取；该脚本同时生成提示正文和确认按钮模板，禁止只凭通用按钮点击。

真实运行发现尚未建模的新阻塞界面时，先保留全屏、动作区域、窗口/进程清单和当前日志。
能够确认会重复出现的界面必须补成“模板、状态分支、动作后验收、回归测试”；无法判断
是一次性还是周期性时，先请用户确认分类，不得静默跳过或仅靠人工救回本轮。

每次业务流程开始前还会在一次性子进程中检查宿主适配器依赖的 OK-WW 类和方法。
上游更新改变接口时会在启动游戏任务前明确失败、保存日志和截图，不会改写或降级
上游安装文件。

讨伐强敌若出现角色死亡，宿主恢复流程在复苏弹窗、挑战失败界面，或“切人持续
10 秒失败且队伍 HUD 仍可见”任一边界成立时介入。第三种用于覆盖上游仍把死亡角色
留在队伍栏、反复切换却不弹复苏框的问题；普通丢目标和技能失败不会单独触发。
流程会保留截图、停止已失败的 OK Worker、退出副本并传送回血，再按实际成功吸收
声骸数计算剩余次数。全过程把持久 `Repeat Farm Count` 固定为原始的 5，禁止改成
1、12 或 60；若再次死亡，仍先安全退本回血。每新增一次确认吸收就清零连续无进度
计数并重置无进度时窗，因此有进度时 Worker 恢复不设总次数上限，直到 `5/5`；只有
连续 3 名 Worker 均无新增吸收才停止。该流程不修改 OK-WW 源码，也不消耗复苏药。

进入讨伐前，宿主覆盖层会用 OCR 确认索拉指南确实位于“讨伐强敌”页面；如果
F2 分类点击被客户端更新或场景恢复吞掉，先重新选择强敌分类，避免把“活跃行迹”
里的通用“前往”按钮误当成 Boss 入口。仍发生 `Teleport to boss failed` 时，
会在同一个 1 小时吸收预算内重启剩余次数；这种入口重试不会被汇报成倒地回血。

每日总控先独立执行讨伐强敌，再启动纯 DailyTask；OK 的
`Additional Tasks to Run After Daily Task` 永久不包含
`Teleport and Farm 4C Echo`，配置预检会拒绝把它重新打开，以免同一天重复讨伐。
两个阶段共用一次 UU/游戏生命周期，并在结束后合并为一条日报。

讨伐任务只有实际吸收声骸达到 `5/5` 才判定完成。击杀、重开界面和
`farm echo ... None` 均不增加该完成进度；不足 5 次时会在进入 DailyTask 前补齐。
每次新增吸收都会重置 1 小时无进度时窗；若最终未到 `5/5`，DailyTask 不会在异常
客户端上继续启动，而是明确记录跳过并执行完整清理。
前置讨伐、死亡恢复、DailyTask 及其重试属于同一个业务事务：中间尝试只保存日志和截图，
不发送飞书；达到 `5/5`、触发无进度保护或遇到不可恢复错误后，才以合并结果发送
唯一一条最终通知。独立人工补跑是新的业务事务，不用于拼接已结束的日报。

## 游戏启动参数

鸣潮 3.7 起直接运行 `Wuthering Waves.exe` 必须带资源包参数 `-krqlv=hd|sd|uhd`，否则游戏约
9 秒后崩溃（`kuro: Use launcher to start game!`）。OK-WW v3.6.7 不带该参数，宿主在
`okww/game_launch.py` 里运行时补上（档位 `GAME_PACKAGE`，本机是高清 `hd`）；OK-WW
发布含修复的正式版后可删除该模块。所有拉起 OK-WW 的入口都必须先装这个补丁：日常、讨伐、
恢复各 worker 自己调用，周常乐园和独立讨伐经 `okww/ok_main_worker.py` 包一层再执行上游
`main.py`。排查启动失败先看 OK 日志里 `try execute ...Wuthering Waves.exe` 后面是否带参数，
再看游戏目录 `Wuthering Waves Game/Client/Saved/Crashes/_0000/`。

版本更新可能在 F2 列表里插入新项，配置里的序号会指到别的目标（1004：无音区第 2 项从
玄幽东岳变成新地图烬心域，传送不了）。版本日后先核对 OK-WW 配置里的无音区、讨伐序号。

## 汇报规则

飞书卡片由程序按固定规则生成，不调用 AI：标题写结论和完成时间，其次是用时；
没全部完成时先列「异常记录」（失败原因已翻译成中文），再列「今日任务」，每个任务
一行，行首 ✅/❌/⚠️ 表示结果，按日常、周常、讨伐的顺序排列。

- 邮件完全不进入报告。
- 只写本轮真正执行的事项；检查后发现早已完成的项目不写。
- 先约电台只有进入实际奖励领取分支时才写。
- 讨伐一行写吸收声骸进度（例如 `5/5`）；击败次数多于吸收时补写击败次数，
  途中团灭、倒地、重启游戏、续跑等自动恢复经过写在同一行。`start wait in combat`
  和 `farm echo ... None` 都不能单独证明击杀，完成只认实际吸收声骸 `5/5`。
- 讨伐行保留「讨伐强敌第N项」原始编号；在 `UserContext/讨伐Boss.md` 登记后，
  编号后面会补上 Boss 名。
- 同一天讨伐和日常分开跑完时，合并成一张当天日报；每个阶段以最近一次结算为准，
  补跑成功的阶段不再显示早上的失败说明。
- 未显式设置 `WUWA_FEISHU_SEND_ENABLED=true` 时只保存飞书预览。

历史运行预览（打印卡片文字，只写 `.preview.json`，不发送）：

```powershell
uv run wuwa-auto report 20261001_054202_farm_echo_confirmed_retry_daily
```

## 星铁联动

正式总控位于总仓 `orchestrator/run.ps1`；本目录的
`scripts/run_daily_chain.ps1` 仅为兼容转发器。总控使用全局锁按顺序执行：

1. 星铁日常
2. 星铁安全清理
3. 鸣潮日常（星铁业务失败时仍继续）
4. 鸣潮自身收尾

只有星铁桌面环境无法安全清理时才跳过鸣潮，避免两个游戏或两种 UU 加速
发生冲突。注册脚本会创建每天本地时间 05:30 的 `Game_Daily_0530`，并删除
已退役的 `StarRail_Main_0600` 与 `StarRail_Cleanup_0800`。

幻梦游园不再放在每日 OK-WW 配置中，而由
`Game_Wuwa_WeeklyGarden_Sunday` 每周日 08:00 独立执行。两项计划任务复用同一
全局互斥锁；周常遇到仍在运行的每日总控时最多等待 3.5 小时，释放后才启动。
日常与周常各自收敛并各发一条最终飞书，不共享日志切片或报告。日常计划任务仍
以 3 小时为硬保险；周常计划任务的 8 小时上限包含锁等待和自身运行时间。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/register_chain_task.ps1
powershell -ExecutionPolicy Bypass -File scripts/register_weekly_garden_task.ps1
```

计划任务要求当前用户的交互式桌面会话，并以最高权限运行。
